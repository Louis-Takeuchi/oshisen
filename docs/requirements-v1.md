**結論：オシセン選挙サイトは「政策で出会い、人柄で興味を深め、一次情報へ送る」構造で統一します。**

以下を、**デザイン・開発・ASTLA等の生成AIすべてに共通で使える正式な要求定義**としてまとめます。YouTube / Podcast導線も反映済みです。

# オシセン

## 2026年 茨城県議会議員選挙 Webサイト 要求定義書

Version 1.0

---

# 1. プロジェクト概要

## 1-1. サービス名

**オシセン**

## 1-2. 対象

2026年 茨城県議会議員選挙

Phase 0 実証プロジェクト

## 1-3. サービスの目的

オシセンは、候補者の政策だけでなく、

* 人柄
* 経歴
* 日常
* 人生経験
* 意思決定の癖
* 価値観
* 失敗
* 挑戦
* 本人の言葉

などを知ることで、

**「この候補者をもう少し知ってみたい」**

という感情を生み出す政治家発見サービスである。

ただし、今回のPhase 0では、

**政策による候補者マッチングを起点とする。**

人柄情報は政策の代わりではない。

政策を見た上で候補者に興味を持ち、さらに情報探索してもらうための追加レイヤーとして扱う。

---

# 2. ブランドの基本思想

## MISSION

**政治家との出会い方を、変える。**

## VISION

**「今回、誰が気になる？」が、ふつうに交わされる社会へ。**

## ユーザー向けコピー

**政治家の気にピ、つくってみない？**

## 世界観

**政治って、人で見るとちょっとおもろい。**

---

# 3. サービス設計の大原則

サイト全体は、以下の順序で設計する。

**政策**
↓
**候補者を知る**
↓
**人となりを知る**
↓
**本人の長い話を聞く**
↓
**公式情報・一次情報を見る**

つまり、

**政策 → 興味 → 人 → 深掘り → 一次情報**

という導線を作る。

「人柄が良さそうだから投票しよう」という設計にはしない。

人柄情報は、

**政策についてさらに調べるきっかけ**

として位置づける。

---

# 4. プロダクト仮説

中心となる仮説は以下。

> 政策情報だけでは候補者を深く調べなかったユーザーでも、候補者の人間性が見える情報を追加することで、候補者について追加的な情報探索を行う可能性が高まるのではないか。

この仮説を検証できるWebサイトにする。

---

# 5. 想定ユーザー

中心ユーザー：

* 18〜25歳程度
* 政治に強い関心があるわけではない
* 候補者名をほとんど知らない
* SNS経由でアクセスする可能性が高い
* スマートフォン利用が中心
* 政策比較には多少関心がある
* 長い選挙公報を最初から読むほどではない

ただしUI上では、

**「若者向け政治サイト」**

を過剰に主張しない。

若者を子ども扱いしない。

* 候補者公式サイト
* YouTube
* 選挙公報
* X
* Instagram
* 議会記録

# 10. TOPページの目的

ユーザーが5秒以内に、

**「質問に答えると、自分と政策の近い候補者を知れるサイト」**

だと理解できる状態にする。

長いサービス説明を最初に置かない。

# 11. TOP / Hero

小ラベル：

**2026 茨城県議会議員選挙**

メインコピー：

# 政治家の気にピ、

# つくってみない？

サブコピー：

**いくつかの質問に答えると、
あなたと政策の近い候補者が見つかります。**

補足：

**まずは政策から。
気になったら、その人自身まで。**

Primary CTA：

**診断をはじめる →**

Secondary CTA：

**候補者から見る**

# 12. Heroビジュアル

抽象的なAI生成ビジュアルは禁止。

候補者写真を使用する場合は、

* 実写
* 同程度の画角
* 同じアスペクト比
* 同程度の大きさ

で統一する。

候補者をランダムまたは公平なルールで配置する。

特定候補だけ大きくしない。

---

# 13. TOP / Concept

見出し：

## 政策だけじゃ、わからないこともある。

本文：

候補者を選ぶとき、政策は大事です。

でも、

どんな経験をしてきたのか。
どんなことで迷うのか。
どういう基準で決断するのか。

そんな情報を知ることで、
政策の見え方が少し変わるかもしれません。

オシセンでは、まず政策との一致度を示した上で、
候補者本人について知るための情報も掲載します。

以下の3段階を表示。

01

**質問に答える**

↓

02

**近い候補者を知る**

↓

03

**気になった人を、もう少し見る**

典型的な「3枚カード」UIは禁止。

雑誌的・エディトリアルな横配置や文字組みで表現する。

# 15. TOP / 候補者への入口

候補者一覧への導線を設置。

「全候補者を見る」

など。

診断を受けないと候補者情報が見られない設計にはしない。

# 16. 診断開始ページ

見出し：

# まずは、あなたの考えを教えてください。

本文：

**正解はありません。
「どちらかといえば」で答えて大丈夫です。**

所要時間は実測値のみ表示可能。

CTA：

**質問をはじめる**

注意：

**回答によって特定候補への投票を勧めるものではありません。**

# 17. 質問回答画面

この画面は、極力シンプルにする。

上部：

* オシセン
* 現在位置
* プログレス

例：

07 / 18

中央：

質問文

例：

**公共交通への行政支援を、今より増やすべきだと思う。**

回答：

* 強くそう思う
* ややそう思う
* どちらともいえない
* あまりそう思わない
* まったくそう思わない

---

# 18. 質問画面UI

選択肢は、

白背景＋border

を基本とする。

選択時のみアクセントカラー。

派手なアニメーション禁止。

遷移は150〜250ms程度。

プログレスバーは細くする。

巨大な数字による進行表示は禁止。

を開くことで、

* 背景
* 用語解説
* 前提

を確認できるようにしてよい。

ただし回答を誘導する説明は禁止。

# 22. 一致度表記ルール

# 23. 結果ページ / 人柄導線

政策結果の直後に、

「性格相性」

などを表示しない。

十分な余白を入れる。

## ところで、この人たち。

## 政策以外はどんな人なんだろう。

本文：

**政策だけでは見えない、
考え方や経験、日常についても聞きました。**

候補者ごとに、

「その人らしさが見えた質問」

を数問表示する。

# 29. 政策詳細

巨大なレーダーチャートだけで済ませない。

# 30. 一致しなかった政策

一致していない論点も隠さない。

**「考えが違ったテーマ」**

を確認できるようにする。

候補者への好意的な誘導を避ける。

# 31. 人となりセクション

補足：

**政策から少し離れて、

# 32. 人柄コンテンツ

候補質問例：

* 休日の過ごし方
* 最近うれしかったこと
* 一番大きな失敗
* 人生で影響を受けた人
* 判断するとき直感とデータどちらを信じるか
* 自分の性格を一言で表すと
* 政治家になっていなかったら何をしていたか
* 最近挑戦したこと
* 苦手なこと
* 若い頃と考えが変わったこと

すべてカード型にしない。

記事を読むようなレイアウトとする。

# 33. 人柄情報の編集方針

候補者を、

「親しみやすいキャラクター」

として加工しすぎない。

運営側による過度な脚色は禁止。

* 情報量
* 表示場所

# 42. 必須注意書き

以下の趣旨を掲載。

**オシセンは、特定の候補者への投票を推奨・依頼するサービスではありません。**

**政策一致度は候補者の優劣を示すものではありません。**

**掲載情報は可能な限り候補者本人の回答や一次情報を確認しています。**

# 43. 実験設計

Phase 0では、

政策情報のみを見るユーザー

と、

政策情報に加えて人柄情報を見るユーザー

の行動差を分析できる状態を目指す。

必要であれば、

A：
政策中心

B：
政策＋人柄

のA/B比較を実施可能な構造とする。

# 77. 最終原則

**政治を軽くするのではなく、政治への入口を軽くする。**

**人柄を政策の代わりにしない。**

**政策で出会い、人柄で興味を深める。**

**候補者を推すのではなく、候補者を知るきっかけを作る。**

**オシセンの中で完結させず、本人の一次情報へ送る。**

**若者向けだからといって、若者を子ども扱いしない。**

**UIを面白くするのではなく、候補者という人間そのものを面白く見せる。**

**装飾ではなく、編集と情報設計で完成度を作る。**

## 根拠

今回の要件で特に重要なのは、**オシセンを「人柄マッチングサイト」にしないこと**です。政策マッチングが入口であり、人柄はその後の情報探索を促すための仕組みです。

そのため、サイト全体で最も重要なファネルは、

**診断完了 → 候補者詳細 → 人柄閲覧 → YouTube / 公式サイト等への遷移**

になります。

## 具体的なアクション

次はこの要求定義をそのままASTLAに入れるより、ここから**ASTLA専用の「制作命令プロンプト」へ変換する**のが適切です。要求定義書は「何を作るか」、ASTLA用プロンプトは「どう作らせるか」で分けた方が生成精度が上がります。

## 代替案

さらに精度を上げるなら、次に作るべきなのは文章ではなく、**TOP・質問・結果・候補者詳細の4ページについて、PC / Mobileそれぞれの画面設計書**です。「この位置にこの要素」「この順番」「ここはカード禁止」まで固定できます。

## リスク・注意点

最大のリスクは、デザインを詰めるうちに「人柄」が目立ちすぎ、**政策比較より候補者のキャラクター消費が中心になること**です。YouTubeも同様で、あくまで深掘り導線として扱うべきです。

また本番時は、公平性・候補者情報の出典・一致度ロジック・表示順について、デザイン以上に厳密な運用ルールが必要です。確信度：高。
